# GrowVision — Спецификация Telegram-бота (MVP)

Документ полностью описывает Telegram-бот GrowVision (`clients/telegram_bot/`): архитектуру, конфигурацию, структуру модуля, роли и меню, пагинацию, пользовательские сценарии, таймауты и обработку ошибок.

Опирается на `DB_SCHEMA.md`, `API_CONTRACT.md`, `REPO_AND_VERSIONING.md` и симметричен по терминам и поведению с `CLI_SPEC.md`.

---

## 1. Назначение и архитектурные ограничения

- **Статус документа:** защищённый архитектурный документ (меняется только с согласия пользователя, `REPO_AND_VERSIONING.md`, раздел 5.3).
- **Стек:** Python 3.11+, `aiogram` 3.x (FSM на `MemoryStorage`), `httpx` (`AsyncClient`), `python-dotenv`. Режим работы: long polling.
- **Развёртывание:** рядом с сервером на том же ПК, `venv` + `systemd`, без Docker.
- **Строгая изоляция:** бот — тонкий REST-клиент. Он живёт в `clients/telegram_bot/` со своим `venv` и `requirements.txt`. Импорт кода из `server/`, `edge_agent/` и `shared/`, обращение к SQLite и к файлам `server/media/` по пути на диске **запрещены**. Данные, картинки и видео бот получает только по HTTP: Client API и статика `/media/...` по `SERVER_URL`.
- **Язык интерфейса:** весь интерфейс (кнопки, заголовки, подсказки) на понятном русском языке, без технического сленга в пользовательских текстах. Все метки времени выводятся в UTC с пометкой `UTC`.
- **Версия:** бот не содержит собственной версии и не читает `VERSION`. Версию системы бот получает у сервера через публичный `GET /api/version` и показывает в справке (см. 3 и 5.1).

### 1.1. Конфигурация (`clients/telegram_bot/.env`)

Шаблон — `clients/telegram_bot/.env.example`, чтение через `python-dotenv`.

| Переменная | Обязательная | Описание |
| :--- | :---: | :--- |
| `TELEGRAM_BOT_TOKEN` | да | Токен бота. |
| `SERVER_URL` | да | Адрес сервера для обращения бота (например, `http://127.0.0.1:8000`). |
| `CLIENT_API_KEY` | да | Секретный ключ клиентов (совпадает с `server/.env`). |
| `WEB_PUBLIC_URL` | нет | Адрес веб-плеера, доступный **пользователям** (например, `http://192.168.1.10:8000`). `SERVER_URL` для этого не подходит: `127.0.0.1` недоступен с телефона. Если не задан, кнопка и ссылка на веб-плеер не показываются. |
| `TELEGRAM_PROXY` | нет | Прокси для обращений к Telegram API (`http://` или `socks5://`, например `socks5://127.0.0.1:1080`). Если пусто или не задан — прямое подключение. |
| `BOT_DEBUG_LOG` | нет | Включение подробного структурированного JSONL-журнала в `clients/telegram_bot/logs/` (`true`/`false`, по умолчанию `false`). Хранение 7 дней. |

- Паролей ролей (`BIOLOGIST_PASSWORD`, `DEVELOPER_PASSWORD`) в `.env` бота нет: пароль проверяет только сервер.
- Если не заданы обязательные переменные, бот не запускается и пишет в лог, каких именно не хватает.

### 1.2. HTTP-заголовки и роль пользователя

В каждый запрос к `/api/*` бот подставляет:

- `X-Client-Key: <CLIENT_API_KEY>`
- `X-Client-Type: telegram`
- `X-External-Id: <str(from_user.id)>`

Правила:

- Источник истины по роли и правам — сервер (`API_CONTRACT.md`, раздел 1.1). Reply-клавиатура — только подсказка интерфейса; любое действие всё равно проверяется сервером.
- Публичные эндпоинты (`GET /api/version`, `GET /api/installations`, `GET /api/installations/{id}`, `GET /api/timelapse/{id}/frames`) для пользователя без сессии работают как для Гостя, `401` на них возможен только при неверном `CLIENT_API_KEY`.
- Если на защищённый эндпоинт пришёл `401` (сессия не найдена или сброшена), бот сбрасывает меню в интерфейс Гостя и предлагает войти.

## 3. Роли и главное меню

При `/start` и при каждом возврате в главное меню бот определяет роль через `GET /api/auth/me`: `200` → `biologist` или `developer`, `401` → Гость. Затем показывает нижнюю Reply-клавиатуру роли.

Общие команды: `/start`, `/help`, `/version`, `/login`, `/cancel` (отмена любого шага FSM). Справка (`ℹ️ Справка`, `/help`) содержит описание ролей и возможностей, а также строку `Версия системы: <server_version>` (если сервер недоступен, строка опускается без ошибки). `/version` выводит только версию.

### 3.1. Гость (неавторизованный пользователь)

- **Возможности:** список активных установок и их карточки (публичные поля: название, культура, последняя площадь), просмотр плановых кадров, ссылка на веб-плеер, справка, вход.
- **Меню:**
  - `[ 🌱 Установки ]`
  - `[ 🔑 Войти ] [ ℹ️ Справка ]`

### 3.2. Biologist

- **Возможности:** всё, что у Гостя, плюс привязанные камеры (без `hardware_id`) и размер ArUco в карточке; изменение названия и культуры установки; ручной снимок одной установки или всех; получение таймлапса в чат; профиль и выход.
- **Ограничения:** не видит GPIO-пины и `debug_info`, не создаёт, не архивирует и не удаляет установки, не управляет светом, вспышкой и камерами, не меняет системные настройки.
- **Меню:**
  - `[ 🌱 Установки ] [ 📸 Сделать снимок ]`
  - `[ 🎬 Таймлапс (видео) ] [ 👤 Профиль / Выход ]`
  - `[ ℹ️ Справка ]`

### 3.3. Developer

- **Возможности:** полный доступ:
  - активные и архивные установки (с GPIO-пинами и `hardware_id`), создание, полное редактирование, архивация, удаление;
  - камеры: список, сканирование, привязка и отвязка;
  - основной свет, вспышка, тест реле (одна установка или все активные);
  - ручные снимки и таймлапс;
  - статус сервера и RPi, интервал автосъёмки, `debug_mode`;
  - блок `debug_info` под ответами управляющих команд при включённом `debug_mode`.
- **Меню:**
  - `[ 🌱 Установки ] [ 📷 Камеры ]`
  - `[ 💡 Свет и реле ] [ 📸 Сделать снимок ]`
  - `[ 🎬 Таймлапс (видео) ] [ ⚙️ Система ]`
  - `[ 👤 Профиль / Выход ] [ ℹ️ Справка ]`

## 4. Универсальный пагинатор (`keyboards/paginator.py`)

### 4.1. Где применяется

| Список | Размер страницы |
| :--- | :---: |
| Установки (активные / архивные) | 5 |
| Камеры (просмотр, результат сканирования, выбор для привязки) | 5 |
| Выбор целевой установки для действий (снимок, свет, вспышка, тест реле, видео) | 5 |
| Плановые кадры таймлапса | 1 кадр |

- В списке целевых установок закреплена верхняя кнопка `[ 🌐 Все активные установки ]` там, где допустим `target = "all"` (снимок, свет, вспышка, тест реле). Для видео этой кнопки нет.
- Кадры: фото + подпись + кнопки `[ ⏮ В начало ] [ ◀️ Пред. ] [ Кадр X/N ] [ След. ▶️ ] [ В конец ⏭ ]` + переключатель слоя `[ 🖼 Оригинал / 🧠 Разметка ]`.

### 4.2. Правила

- Пагинатор редактирует существующее сообщение (`edit_message_text` / `edit_message_media`), а не отправляет новое при каждом перелистывании.
- Если элементов не больше размера страницы, кнопки `◀️` / `▶️` скрываются.
- `callback_data` компактная, до 64 байт (например, `pag:<entity>:<page>:<extra>`), каждый callback обязательно завершается `await callback.answer()`.
- Ошибка Telegram «message is not modified» игнорируется.
- Для кадров список `frames` один раз загружается при открытии галереи и хранится в FSM-данных пользователя; в `callback_data` передаются только индекс кадра и слой (`r` / `a`). Если данные потеряны (например, перезапуск бота), бот пишет `Сессия просмотра устарела, откройте кадры заново` и возвращает к карточке установки.

## 5. Пользовательские сценарии

### 5.1. Двухэтапная авторизация (`handlers/start_auth.py`)

1. Пользователь нажимает `[ 🔑 Войти ]` или вводит `/login`.
2. **Шаг 1** (`AuthStates.waiting_login`): `Введите ваш логин (имя и фамилию, например: Иван Петров):` + `[ ❌ Отмена ]`.
3. **Шаг 2** (`AuthStates.waiting_password`): `Введите пароль доступа:`. Сразу после получения пароля бот пытается удалить сообщение пользователя (`await message.delete()`, исключение при отсутствии прав перехватывается), чтобы пароль не оставался в переписке.
4. Бот вызывает `POST /api/auth/login` с `client_type = "telegram"`, `external_id = str(from_user.id)`.
   - `200`: очищает FSM, пишет `Вы вошли как <login> (роль: <Биолог|Разработчик>)`, переключает клавиатуру.
   - `401`: `Неверный пароль`, предлагает ввести пароль ещё раз или `[ ❌ Отмена ]`.
   - `429`: время ожидания из `Retry-After`.
5. **Профиль / Выход:** `[ 👤 Профиль / Выход ]` показывает данные `GET /api/auth/me` (логин, роль, время входа и последней активности, UTC) и кнопку `[ 🚪 Выйти ]`. Выход — `POST /api/auth/logout`, очистка FSM, клавиатура Гостя.

### 5.2. Установки (`handlers/installations.py`)

- **Список.**
  - Гость и Biologist видят только активные установки (`include_archived=false`).
  - У Developer вверху переключатель `[ Активные ] / [ Архивные ]` (`include_archived=true`).
  - Нажатие на установку открывает карточку с полями по ролевой проекции из `API_CONTRACT.md`, раздел 4.2. Бот не падает при отсутствии необязательных полей.
- **Кнопки карточки.**
  - Все роли: `[ 🖼 Кадры таймлапса ]`, `[ 🌐 Открыть веб-плеер ]` (если задан `WEB_PUBLIC_URL`), `[ ⬅️ К списку ]`.
  - Biologist (установка не в архиве): `[ 📸 Сделать снимок ]`, `[ 🎬 Скачать видео ]`, `[ ✏️ Изменить название / культуру ]`.
  - Developer (установка не в архиве): `[ 💡 Свет / Вспышка / Тест ]`, `[ 📷 Камеры установки ]`, `[ ✏️ Редактировать ]`, `[ 📦 В архив ]`, `[ 🗑 Удалить ]`.
  - Для архивной установки Developer видит `[ 🎬 Скачать видео ]` и `[ 🗑 Удалить ]`.
- **Ссылка на веб-плеер.** Адрес `WEB_PUBLIC_URL` отправляется обычным текстом в сообщении (а не URL-кнопкой, потому что Telegram может отклонять адреса локальной сети).
- **Создание (Developer, FSM).** Пошаговый мастер: Название → Культура → GPIO-пин света (целое число) → GPIO-пин вспышки (целое число) → Размер стороны ArUco в мм (число > 0 или `[ Пропустить (без маркера) ]`) → `POST /api/installations`. На каждом шаге `[ ❌ Отмена ]`. Ошибки сервера (`409`: имя или пин заняты, `422`) выводятся дословно.
- **Редактирование.**
  - Biologist: выбор `[ Название ]` или `[ Культура ]` → ввод значения → `PATCH /api/installations/{id}`.
  - Developer: inline-меню полей: Название, Культура, Пин света, Пин вспышки, Размер ArUco, `[ Сбросить ArUco ]` (передаётся `null`).
- **Архивация и удаление (Developer).** Обязательный экран подтверждения `[ ✅ Да, подтвердить ] / [ ❌ Отмена ]`. При `409` на удаление (есть снимки) бот выводит текст сервера и предлагает `[ 📦 Перевести в архив ]`.

### 5.3. Камеры (`handlers/cameras.py`, только Developer)

- **Раздел:** список зарегистрированных камер (`GET /api/cameras`, пагинатор) и кнопка `[ 🔍 Сканировать камеры на RPi ]`. В списке у каждой камеры: модель, `Online` / `Offline`, привязка.
- **Сканирование:** `POST /api/cameras/scan`, статус `Сканирую USB-камеры на Raspberry Pi...`. Бот показывает **все камеры, обнаруженные при сканировании** (пагинатор). Для каждой:
  - `Свободна — можно привязать` (кнопка `[ 🔗 Привязать ]`), если `installation_id = null`;
  - `Привязана к установке «<installation_name>»`, если `installation_id` заполнен.
  - Пометки «новая» нет. Если камер нет: `Камеры не обнаружены. Проверьте USB-подключение камер к Raspberry Pi`. Под результатом — блок DEBUG (если включён).
- **Карточка камеры:** `[ 🔗 Привязать к установке ]` (пагинатор активных установок, `POST /api/cameras/{id}/bind`) или `[ ⛓ Отвязать от установки ]` (`{"installation_id": null}`). К одной установке можно привязать несколько камер; привязка к архивной установке даёт `409`, текст сервера выводится дословно.

### 5.4. Свет и реле (`handlers/control.py`, только Developer)

- Выбор цели: `[ 🌐 Все активные установки ]` или установка из пагинатора.
- Панель цели:
  - `[ 💡 Основной свет: ВКЛ ] / [ ВЫКЛ ]` → `POST /api/control/light/main`;
  - `[ ⚡ Вспышка: ВКЛ ] / [ ВЫКЛ ]` → `POST /api/control/light/flash`;
  - `[ 🧪 Тест реле (3 сек) ]` → `POST /api/control/relay-test`.
- Результат: статус выполнения в том же сообщении. Если `status = "error"`, выводится `result_message`. При включённом `debug_mode` под ответом блок DEBUG (`command` + `log_line`).

### 5.5. Ручной снимок (`handlers/control.py`, Biologist и Developer)

- Выбор цели: `[ 🌐 Снять все установки ]`, установка из пагинатора или запуск из карточки.
- Бот отправляет `⏳ Делаю снимок, подождите...` и вызывает `POST /api/control/snap`.
- `status = "done"`: для каждого элемента `captures` бот скачивает `raw_url` и `annotated_url` (`SERVER_URL` + url) и отправляет альбом из двух фото (оригинал + разметка). Подпись у первого фото: название установки, камера (`ID`), время съёмки UTC, площадь (`area_display`, например `48.3 см²` или `15430 px`; `null` — `площадь не определена`). Названия установок берутся из ранее полученного списка (при необходимости повторный `GET /api/installations`). Ручные кадры в таймлапс не входят — бот пишет об этом один раз в подписи к последнему альбому. Для Developer при `debug_mode = true` добавляется блок DEBUG.
- `status = "error"` (например, камера занята плановой съёмкой): индикатор заменяется текстом `result_message` (`Камера недоступна, попробуйте позже`).

### 5.6. Таймлапс (`handlers/timelapse.py`)

#### 5.6.1. Просмотр кадров (все роли)

1. Бот вызывает `GET /api/timelapse/{id}/frames` (без `camera_id`) и сохраняет список в FSM-данных.
2. Если плановых кадров нет, `frames` пуст: `Плановых кадров пока нет. Они появятся после первой автосъёмки.`
3. Выбор камеры по тому же правилу, что в веб-плеере (`WEB_SPEC.md`, раздел 4.1): бот ищет **соседние** (по времени) кадры с разными `camera_id`, снятые с разницей не более 10 минут (камеры снимали одновременно). Если такие есть, предлагается выбрать `[ Камера <id> ]` (пункта «Все камеры» нет, чтобы не смешивать ракурсы; названий камер у Гостя нет, подписи по `ID`; фильтрация на стороне бота по уже загруженному списку). Если нет (камера одна или камера заменена без пересечения по времени), галерея открывается сразу одной непрерывной лентой.
4. Галерея открывается на **самом свежем** кадре. Пагинатор листает по одному кадру (`edit_message_media`, `InputMediaPhoto`), слои `raw_url` / `annotated_url`. Подпись: установка, камера, время UTC, `area_display`.

#### 5.6.2. Сборка и отправка видео (Biologist, Developer)

1. **Выбор цели:** установка из пагинатора (без `все`), доступны и архивные установки для Developer (через фильтр в списке).
2. **Выбор камеры.** Если у установки привязано больше одной камеры (`cameras[]` карточки), обязательный шаг выбора камеры (`camera_id`). Если камера одна или привязанных нет, `camera_id` не передаётся. Если сервер всё же вернул `422` про несколько камер, бот выводит `detail` дословно и добавляет: `Выберите камеру или скачайте видео через CLI: snap video <ID> --camera-id <id>`.
3. **Защита от повторного запуска:** у пользователя одновременно может собираться только одно видео; повторное нажатие пока идёт сборка отвечает `Видео уже собирается, подождите`.
4. **Попытка 0 (полный таймлапс).** Статус `⏳ Собираю видео таймлапса. Для длинных таймлапсов это может занять несколько минут...`. Запрос `POST /api/timelapse/{id}/video` с телом `{"camera_id": <id|null>, "step": 1}` (потоковая загрузка, см. 6).
5. **Разбор ответа:**
   - `404`: `Плановые снимки не найдены` (текст сервера) + подсказка: плановые снимки появятся после первой автосъёмки, ручные снимки в таймлапс не входят.
   - `Content-Type: image/jpeg` (плановый кадр один): бот отправляет его как фото (`answer_photo`) с подписью `Плановый кадр пока один, видео не собрано`.
   - `video/mp4`: проверка размера (см. ниже).
6. **Лимит Telegram.** Бот принимает видео до `TG_VIDEO_LIMIT = 50 000 000` байт (лимит Bot API — 50 МБ; константа берётся с запасом). Размер определяется по заголовку `Content-Length` до скачивания тела; если заголовка нет, файл скачивается во временный файл и проверяется после загрузки. Файл больше лимита не скачивается и не отправляется.
7. **Цикл прореживания.** Если видео больше лимита, бот запускает до **5** циклов, в каждом `step = 2^k` (`2, 4, 8, 16, 32`):
   - в начале цикла бот обновляет статусное сообщение: `Видео получилось слишком большим для Telegram (лимит 50 МБ). 🔄 Попытка <k> из 5: собираю заново с прореживанием, берётся каждый <step>-й кадр...` (для первого цикла сообщение объясняет причину, для следующих — `🔄 Попытка <k> из 5: видео снова слишком большое, собираю заново, каждый <step>-й кадр...`);
   - выполняется `POST .../video` с `{"camera_id": ..., "step": <step>}`;
   - если размер уложился в лимит, цикл заканчивается отправкой.
8. **Отправка.** Видео отправляется через `answer_video` (`supports_streaming=True`; при отказе клиента воспроизводить — `answer_document`). Подпись: название установки (и камера, если выбрана).
   - Полное видео: `Таймлапс: <название>`.
   - Прореженное: `Таймлапс: <название>. Прореженная версия: каждый <step>-й кадр. Полную версию можно скачать через консольный клиент (CLI): snap video <ID>`.
9. **Исчерпание циклов.** Если после 5 циклов (`step = 32`) видео всё ещё больше лимита, бот ничего не отправляет и пишет: `Не удалось уложить видео в лимит Telegram (50 МБ) даже при каждом 32-м кадре. Полную версию можно скачать через консольный клиент (CLI): snap video <ID>`.
10. Временные файлы всегда удаляются, флаг «видео собирается» снимается в любом исходе (включая ошибки).

### 5.7. Система и настройки (`handlers/system.py`, только Developer)

- **Статус** (`GET /api/system/status`): версия сервера, связь с RPi (`🟢 Online` / `🔴 Offline`), время последнего heartbeat, версия `edge_agent`, модель нейросети, температура CPU, загрузка CPU и RAM, свободное место на диске RPi, `offline_queue_count`, интервал автосъёмки, `debug_mode`. Кнопки: `[ 🔄 Обновить ]`, `[ ⏱ Изменить интервал съёмки ]`, `[ 🐞 Вкл/Выкл Debug-режим ]`.
- **Интервал съёмки (FSM):** целое число часов ≥ 1 или быстрые кнопки `1 ч, 2 ч, 4 ч, 6 ч, 12 ч, 24 ч`. После `PATCH /api/system/settings` бот выводит поле `warning` (о неравномерном шаге таймлапса), если оно пришло в ответе.
- **Debug-режим:** `PATCH /api/system/settings` с `{"debug_mode": true|false}`.

## 6. Таймауты и обработка ошибок

### 6.1. Таймауты `httpx.AsyncClient`

| Группа | Таймаут | Обоснование |
| :--- | :---: | :--- |
| Обычные запросы (`auth`, `installations`, `cameras` list/bind, `system`, `version`, `frames`) | `15 с` | Быстрые операции сервера. |
| Одиночные команды (`light *`, `relay-test`, `cameras/scan`, одиночный `snap`) | `35 с` | Серверное ожидание 10–15 с плюс запас. |
| Массовый снимок (`snap`, `target = "all"`) | `30 + 10 × N с` | `N` — число активных установок (серверное ожидание `15 + 10 × N` с плюс запас). |
| Сборка видео (`POST .../video`) | `600 с` на чтение, подключение `10 с` | Сервер собирает все плановые кадры; для длинных таймлапсов сборка занимает минуты (как в CLI). |

- Видео запрашивается потоково (`client.stream`), чтобы проверить `Content-Length` до скачивания тела.
- Для отправки видео в Telegram таймаут сессии `aiogram` увеличивается до `300 с` (по умолчанию слишком мал для файлов десятки мегабайт).

### 6.2. Маппер ошибок (`utils/errors.py`)

Формат ошибок сервера — `{"detail": "..."}` (`API_CONTRACT.md`, разделы 1 и 4.7). Бот выводит `detail` дословно и добавляет подсказку. Если `detail` не строка или тело не JSON, выводится общий текст `Получен некорректный ответ от сервера`.

| Код | Сообщение бота |
| :---: | :--- |
| `401` | Сессия не найдена или неверный пароль. Меню сбрасывается в роль Гость, предлагается `[ 🔑 Войти ]`. Если `401` пришёл на публичный эндпоинт (неверный `CLIENT_API_KEY`), пользователю: `Сервис временно недоступен`, в лог бота: `Проверьте CLIENT_API_KEY`. |
| `403` | `Недостаточно прав: <detail>` |
| `404` | `Не найдено: <detail>`; предлагается вернуться в меню, если установку или камеру уже удалили |
| `409` | `Действие невозможно: <detail>` |
| `422` | `Ошибка данных: <detail>` |
| `429` | `Слишком много попыток входа. Повторите через <Retry-After> сек.` |
| `503` | `Raspberry Pi сейчас не в сети: <detail>` |
| `504` | `Raspberry Pi не ответила вовремя: <detail>`. Для команд управления и съёмки добавляется: `Результат неизвестен, проверьте состояние установки` |
| `5xx` | `Внутренняя ошибка сервера (HTTP <код>). Сообщите разработчику` |
| `httpx.ConnectError` / `TimeoutException` | `Сервер GrowVision временно недоступен. Попробуйте позже` |
