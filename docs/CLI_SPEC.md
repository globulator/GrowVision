# GrowVision — Спецификация CLI-клиента (MVP)

Документ полностью описывает консольный клиент GrowVision (`clients/cli/`): архитектуру, конфигурацию, режимы работы, дерево команд, резолвинг целей, обработку ошибок и форматы вывода.

Опирается на `DB_SCHEMA.md`, `API_CONTRACT.md` и `REPO_AND_VERSIONING.md`.

---

## 1. Назначение и архитектурные ограничения

- **Статус документа:** защищённый архитектурный документ (меняется только с согласия пользователя).
- **Стек:** Python + `Typer` + `httpx` + `rich` (таблицы, панели, цветовая индикация) + `python-dotenv` (чтение `.env`).
- **Строгая изоляция:** CLI — тонкий REST-клиент. Он живёт в `clients/cli/` со своим `venv` и `clients/cli/requirements.txt`. Импорт кода из `server/`, `edge_agent/` и `shared/`, а также прямое обращение к БД SQLite или папке `server/media/` **запрещены**. Вся работа идёт только через `Client API` (`API_CONTRACT.md`).
- **Конфигурация (`clients/cli/.env`):**
  - `SERVER_URL` — адрес сервера (например, `http://127.0.0.1:8000` или локальный IP сервера).
  - `CLIENT_API_KEY` — секретный ключ доступа к Client API (совпадает с `server/.env`).
  - `CLI_DEBUG` — опциональный флаг (`0` / `1`, по умолчанию `0`) для вывода отладочной HTTP-информации (аналог глобального флага `--verbose`).
  - Паролей ролей (`BIOLOGIST_PASSWORD`, `DEVELOPER_PASSWORD`) в `clients/cli/.env` нет — пароли хранит только сервер.
- **Локальная сессия (`external_id`):**
  - При первом запуске CLI генерирует идентификатор клиента `cli_<uuid4>` и сохраняет его в файл `~/.growvision_cli.json` (вне репозитория, в `.gitignore` не нужен). Если файл отсутствует или повреждён, идентификатор создаётся заново (потребуется повторный вход через `auth login`).
  - В каждый HTTP-запрос подставляются заголовки:
    - `X-Client-Key: <CLIENT_API_KEY>`
    - `X-Client-Type: cli`
    - `X-External-Id: <сохранённый external_id>`
- **Версия:** CLI не содержит собственной версии и не читает `VERSION`. Версия системы берётся у сервера через `GET /api/version` (команда `version`, см. 3.1).

## 2. Режимы запуска и глобальные правила

### 2.1. Два способа запуска

1. **Интерактивная оболочка (`shell`):** запуск `python -m clients.cli.main shell` (или вызов без аргументов) из корня репозитория. Открывается приглашение `growvision> `, в котором команды вводятся напрямую **без префиксов** (`unit list`, `light main all on`, `snap take 1`, `help`, `exit` / `quit`). В баннере оболочки выводится версия сервера (`GrowVision <server_version>`); если сервер недоступен, баннер выводится без версии, без ошибки.
2. **Одиночный вызов из терминала ОС:** `python -m clients.cli.main <команда_или_раздел> [аргументы]` (для скриптов и разовых действий).

### 2.2. Глобальная справка (`help`) и справка разделов (`<раздел> info`)

- **Глобальная команда `help`:** выводит общую информацию о проекте GrowVision, краткое описание ролей (Гость / Biologist / Developer), список глобальных команд (`help`, `version`), список всех 6 корневых разделов с их назначением и базовые примеры начала работы (`auth login`, `unit list`, `snap take 1`).
- **Команда `<раздел> info`:** реализована в каждом из 6 разделов (`auth info`, `unit info`, `camera info`, `light info`, `snap info`, `system info`). Выводит назначение раздела, минимально требуемую роль, полный список подкоманд раздела с аргументами/флагами и 1–2 живых примера запуска.

### 2.3. Резолвер целей (`<target>`)

Везде, где команда принимает целевую установку (`unit show/edit/archive/delete`, `light main/flash/test`, `snap take`, `snap video`, `camera bind`), аргумент `<target>` обрабатывается единой функцией и поддерживает **3 формата**:

1. **Числовой ID установки** (например, `1`) → передаётся в API как `1`.
2. **Уникальное название установки** (например, `"Установка 1 — Фитолампа"`) → CLI предварительно вызывает `GET /api/installations`, ищет точное совпадение по полю `name` и подставляет её `id`. Если установка не найдена, CLI завершается с ошибкой без отправки основной команды. Параметр `include_archived` выбирается по команде:
   - `true` (архивные установки доступны): `unit show`, `unit edit`, `unit delete`, `snap video` (полный таймлапс завершённой установки — штатный сценарий);
   - `false` (только активные): `unit archive`, `camera bind`, `light *`, `snap take`.
3. **Ключевое слово `all`** (регистронезависимо) → применяется ко всем активным установкам:
   - в `/api/control/*` передаётся `"target": "all"`;
   - в `unit show all` CLI вызывает `GET /api/installations` (проекция по роли та же, что и у карточки) и выводит карточки всех активных установок;
   - в командах, где массовое действие запрещено (`unit edit`, `unit archive`, `unit delete`, `camera bind`, `snap video`), при передаче `all` CLI сразу выводит понятную ошибку валидации.

*(Для камер в `camera bind` и `camera unbind` поддерживается резолвинг по числовому `id` или по `hardware_id` через предварительный вызов `GET /api/cameras`.)*

### 2.4. Таймауты HTTP-клиента (`httpx`)

Чтобы CLI не обрывал соединение раньше, чем сервер завершит ожидание Raspberry Pi или сборку видео, используются дифференцированные таймауты:

| Группа эндпоинтов | Таймаут `httpx` | Обоснование |
| :--- | :---: | :--- |
| Обычные CRUD, статус и версия (`auth`, `unit`, `camera list/bind`, `system`, `version`) | `10 с` | Быстрые операции с БД сервера. |
| Одиночные управляющие команды (`light *`, `camera scan`, `snap take <id>`) | `30 с` | Серверное ожидание 10–15 с плюс запас; позволяет получить корректный ответ или `504`. |
| Массовые команды (`target = "all"`) | `30 + 10 × N с` | `N` — число активных установок; серверное ожидание `15 + 10 × N с` плюс запас 15 с. |
| Сборка и скачивание видео (`snap video`) | `600 с` (на чтение) | Сервер собирает **все** плановые кадры установки; для длинных таймлапсов (сотни и тысячи кадров) сборка занимает минуты. Подключение — 10 с. |

### 2.5. Адаптация под ролевые проекции и режим отладки

- **Ролевые проекции:** таблицы и карточки CLI адаптируют набор колонок под фактически пришедшие от сервера поля (у Гостя нет `cameras`, `aruco_size_mm` и GPIO-пинов; у Biologist нет `light_gpio_pin`, `flash_gpio_pin` и `hardware_id` камер) и не падают с `KeyError`.
- **Режим отладки (`debug_info`):** если у пользователя роль `developer` и в ответе `/api/control/*` или `/api/cameras/scan` присутствует объект `debug_info`, CLI выводит его отдельным серым блоком под основным результатом:
  ```text
  --- DEBUG ---
  Команда: {"id": 42, "command_type": "SNAP", "target": 1, "payload": null}
  Лог RPi: [2026-11-18T19:30:02Z] [INFO] [GPIO] Inst#1: light=0, flash=1 -> captured 1 frames
  ```
- **Флаг `--verbose` / `CLI_DEBUG=1`:** при включении выводит перед каждым запросом HTTP-метод и URL, а после ответа — HTTP-статус и сырое тело ответа сервера (для `snap video` тело не печатается, только статус и размер).

## 3. Дерево команд и матрица прав

Корневые сущности: глобальные команды `help`, `version` + 6 разделов (`auth`, `unit`, `camera`, `light`, `snap`, `system`).

### 3.1. Глобальные команды

| Команда | Доступ | API | Поведение |
| :--- | :---: | :--- | :--- |
| `help` | Все | — | Выводит обзор проекта GrowVision, таблицу ролей, глобальные команды, перечень всех 6 разделов CLI и базовые примеры команд. |
| `version` | Все | `GET /api/version` | Выводит версию сервера: `GrowVision server: <server_version>` (например, `0.2.0-b71c4de`). |

### 3.2. Раздел `auth` — Авторизация и управление сессией

| Команда | Аргументы / Флаги | Доступ | API | Поведение |
| :--- | :--- | :---: | :--- | :--- |
| `auth info` | — | Все | — | Справка по разделу `auth` с примерами. |
| `auth login` | — | Все | `POST /api/auth/login` | Интерактивный 2-шаговый ввод (пароль не передаётся через аргументы CLI):<br>1. Запрос логина (непустая строка).<br>2. Скрытый ввод пароля (`hide_input=True`).<br>Выводит: `Авторизация успешна. Логин: <login>, Роль: <role>`. |
| `auth status` | — | Bio / Dev | `GET /api/auth/me` | Выводит текущий логин, роль, время авторизации (`authorized_at`) и последней активности (`last_active_at`). |
| `auth logout` | — | Bio / Dev | `POST /api/auth/logout` | Завершает сессию на сервере; клиент возвращается в роль **Гость**. |

### 3.3. Раздел `unit` — Гидропонные установки

| Команда | Аргументы / Флаги | Доступ | API | Поведение |
| :--- | :--- | :---: | :--- | :--- |
| `unit info` | — | Все | — | Справка по разделу `unit` с примерами. |
| `unit list` | `--archived` (флаг, по умолч. `False`) | Гость / Bio / Dev | `GET /api/installations?include_archived=...` | Выводит таблицу: `ID`, `Название`, `Культура`, `Площадь` (`last_area_display` или `—`), `Статус` (`Активна`/`Архив`) + колонки `Камеры` (для Bio/Dev) и `Light GPIO` / `Flash GPIO` (для Dev). Если список пуст — пишет `Установок пока нет`. |
| `unit show` | `<target>` (`ID`, имя или `all`) | Гость / Bio / Dev | `GET /api/installations/{id}` (для `all` — `GET /api/installations`) | Выводит подробную карточку установки (или всех активных установок для `all`), включая список привязанных камер (`0`, `1` или `N` штук со статусом `online`/`offline`), размер ArUco и последнюю площадь. |
| `unit add` | `--name`, `--culture`, `--light-pin`, `--flash-pin`, `--aruco-mm` (опц.) | Dev | `POST /api/installations` | Если флаги не переданы, запрашивает параметры интерактивно. После `201` выводит созданную карточку установки. |
| `unit edit` | `<target>`, `--name`, `--culture`, `--light-pin`, `--flash-pin`, `--aruco-mm`, `--clear-aruco` (флаг) | Bio (`--name`, `--culture`) / Dev (все) | `PATCH /api/installations/{id}` | Разрешает `<target>` (не поддерживает `all`). Флаг `--clear-aruco` передаёт `"aruco_size_mm": null` для сброса маркера. Выводит обновлённую карточку. |
| `unit archive` | `<target>`, `--yes / -y` | Dev | `POST /api/installations/{id}/archive` | Запрашивает подтверждение `y/N` (если нет `-y`), переводит установку в архив и отвязывает все её камеры. |
| `unit delete` | `<target>`, `--yes / -y` | Dev | `DELETE /api/installations/{id}` | Запрашивает подтверждение `y/N` (если нет `-y`). При `204` сообщает об удалении; при `409` выводит точную причину (есть снимки, нужна архивация). |

### 3.4. Раздел `camera` — Камеры на Raspberry Pi

| Команда | Аргументы / Флаги | Доступ | API | Поведение |
| :--- | :--- | :---: | :--- | :--- |
| `camera info` | — | Все | — | Справка по разделу `camera` с примерами. |
| `camera list` | — | Dev | `GET /api/cameras` | Таблица всех зарегистрированных камер: `ID`, `Модель (auto_name)`, `Hardware ID`, `Статус` (`Online`/`Offline`), `Привязка` (`Установка «X»` или `Свободна`), `Последний сигнал`. |
| `camera scan` | — | Dev | `POST /api/cameras/scan` | Запускает сканирование USB-камер на RPi и показывает **все камеры, обнаруженные при сканировании** (и ранее известные, и найденные впервые; новые регистрируются автоматически как свободные). Колонки: `ID`, `Модель`, `Hardware ID`, `Привязка`: `Свободна — можно привязать` или `Привязана к установке «X»` (по `installation_id` / `installation_name`). Если камер нет — `Камеры не обнаружены. Проверьте USB-подключение камер к Raspberry Pi`. Под таблицей — подсказка: `Свободные камеры можно привязать: camera bind <id> <установка>` + `debug_info`. |
| `camera bind` | `<camera_id_or_hw>` `<target_unit>` | Dev | `POST /api/cameras/{id}/bind` | Привязывает камеру к указанной активной установке (не поддерживает `all`). К одной установке можно привязать несколько камер. |
| `camera unbind` | `<camera_id_or_hw>` | Dev | `POST /api/cameras/{id}/bind` | Отправляет `{"installation_id": null}` и отвязывает камеру от установки. |

### 3.5. Раздел `light` — Управление светом и вспышкой

Все рабочие команды раздела доступны только роли **Developer**.

| Команда | Аргументы / Флаги | Доступ | API | Поведение |
| :--- | :--- | :---: | :--- | :--- |
| `light info` | — | Все | — | Справка по разделу `light` с примерами. |
| `light main` | `<target>` (`ID`, имя или `all`), `<on\|off>` | Dev | `POST /api/control/light/main` | Включает (`true`) или выключает (`false`) основной свет на одной или всех активных установках. Выводит статус выполнения + `debug_info`. |
| `light flash` | `<target>` (`ID`, имя или `all`), `<on\|off>` | Dev | `POST /api/control/light/flash` | Включает или выключает вспышку. Выводит статус выполнения + `debug_info`. |
| `light test` | `<target>` (`ID`, имя или `all`) | Dev | `POST /api/control/relay-test` | Включает основной свет и вспышку одновременно на 3 секунды для проверки реле. Выводит результат + `debug_info`. |

### 3.6. Раздел `snap` — Ручные снимки и экспорт MP4-таймлапса

| Команда | Аргументы / Флаги | Доступ | API | Поведение |
| :--- | :--- | :---: | :--- | :--- |
| `snap info` | — | Все | — | Справка по разделу `snap` с примерами. |
| `snap take` | `<target>` (`ID`, имя или `all`), `--download <папка>` (опц.) | Bio / Dev | `POST /api/control/snap` | Запускает ручной тестовый снимок (показывает индикатор `Выполняется съёмка...`).<br>• При `status == "done"`: выводит таблицу по массиву `captures` (`Installation ID`, `Camera ID`, `Время UTC`, `Площадь` — в `см²` или `px`, `URL оригинала`, `URL разметки`). Если передан `--download <папка>`, скачивает оба файла (`raw` и `ann`) в указанную директорию обычным `GET` по `SERVER_URL` + `raw_url` / `annotated_url` (путь `/media/` публичный, заголовки авторизации не нужны).<br>• При `status == "error"`: выводит точный текст из `result_message` (например, `Камера недоступна, попробуйте позже`).<br>• Для Developer выводит `debug_info` (если включён). |
| `snap video` | `<target>` (`ID` или имя; архивные установки допустимы), `--camera-id <id>` (опц.), `--step <N>` (опц., целое ≥ 1, по умолч. `1` — прореживание выключено), `--out <путь>` (по умолч. `./timelapse_unit_<id>.mp4`, при одном кадре `.jpg`) | Bio / Dev | `POST /api/timelapse/{id}/video` | Запрашивает таймлапс из плановых кадров установки за всю историю (включая кадры сменённых камер). По умолчанию берутся **все** кадры; с `--step N` — каждый N-й (первый и последний кадры сохраняются). Формат: H.264, высота не более 720p; частоту кадров сервер вычисляет по числу кадров (минимальная длительность видео 2 с). Пока идёт сборка, показывает индикатор `Сборка видео... (длинные таймлапсы могут собираться несколько минут)`. Поток пишется в `<out>.part` и после успешного завершения переименовывается в `<out>` (существующий файл перезаписывается). Выводит путь и размер файла.<br>Особые случаи (CLI смотрит на код и `Content-Type` ответа):<br>• нет плановых кадров (`404`): выводит `detail` сервера (`Плановые снимки не найдены`);<br>• плановый кадр один (`image/jpeg`): сохраняет фото вместо видео, расширение в `--out` или в имени по умолчанию заменяется на `.jpg`, выводится `Плановый кадр только один — вместо видео сохранено фото: <путь>`;<br>• `--camera-id` нужен, только если у установки несколько камер снимали одновременно: тогда сервер отвечает `422`, а в `detail` перечислены доступные камеры. |

### 3.7. Раздел `system` — Состояние RPi и глобальные настройки

Все рабочие команды раздела доступны только роли **Developer**.

| Команда | Аргументы / Флаги | Доступ | API | Поведение |
| :--- | :--- | :---: | :--- | :--- |
| `system info` | — | Все | — | Справка по разделу `system` с примерами. |
| `system status` | — | Dev | `GET /api/system/status` | Выводит сводку по серверу (`server_version`, интервал съёмки, `debug_mode`), статусу связи с RPi (`online`/`offline`, время последнего heartbeat), ПО RPi (`edge_version`, Python, `model_name`, режим GPIO) и железу RPi 5 (плата, ОС, аптайм, температура CPU, загрузка CPU, RAM, свободное место на диске, `offline_queue_count`). |
| `system schedule` | `<hours>` (целое число ≥ 1) | Dev | `PATCH /api/system/settings` | Меняет общий интервал автосъёмки в часах. Если сервер вернул `warning` о неравномерном шаге таймлапса, выводит его жёлтым предупреждением. |
| `system debug` | `<on\|off>` | Dev | `PATCH /api/system/settings` | Включает (`true`) или выключает (`false`) режим отладки. |

## 4. Обработка ошибок

Ни одна команда не завершается молча и не выбрасывает пользователю сырой Python Traceback при штатных ошибках. Любая неуспешная операция завершается с кодом возврата `1` и выводит в `stderr` структурированное сообщение по шаблону:

```text
Ошибка (<контекст действия>): <дословный detail от сервера>
Рекомендация: <конкретное действие для исправления>
```

Текст `detail` от сервера всегда выводится **дословно** и не подменяется общей фразой.

### 4.1. HTTP-ошибки API

| Код | Контекст и дословный `detail` | Подсказка от CLI |
| :---: | :--- | :--- |
| `401` | Нет сессии / неверный пароль / неверный `CLIENT_API_KEY` | Если проблема в сессии — `Выполните вход: auth login`. Если неверный ключ — `Проверьте CLIENT_API_KEY в clients/cli/.env`. |
| `403` | Недостаточно прав роли | `Эта операция доступна только для роли Developer. Проверьте текущую роль: auth status.` |
| `404` | Объект не найден (`detail` от сервера); для `snap video` — у установки нет плановых кадров | `Проверьте список доступных объектов через unit list или camera list.` Для `snap video`: `Плановые снимки появятся после первой автосъёмки по расписанию; ручные снимки (snap take) в таймлапс не входят.` |
| `409` | Конфликт (`detail`: имя занято, пин занят установкой «X», установка в архиве, есть кадры при удалении, нет активных установок) | Подсказка по контексту: указать другой GPIO-пин (`--light-pin` / `--flash-pin`), использовать `unit archive <target>` вместо удаления или создать активную установку. |
| `422` | Ошибка валидации (`detail`: неверный тип поля; для `snap video` — у установки несколько камер, а `--camera-id` не указан, либо `step` не целое ≥ 1) | Подсказка по контексту: для видео — `Укажите --camera-id <id> из списка камер в сообщении выше`; для `--step` — `Укажите целое число не меньше 1`. |
| `429` | Превышен лимит попыток входа | `Повторите попытку через <Retry-After> сек.` |
| `503` | Raspberry Pi офлайн (`detail` от сервера) | `Проверьте питание Raspberry Pi 5 и сетевое подключение (system status).` |
| `504` | Таймаут ожидания ответа RPi (`detail` от сервера) | `Если выполнялась команда управления светом или съёмкой, её фактический результат неизвестен — проверьте состояние через system status или unit show.` |
| `5xx` | Внутренняя ошибка сервера (`500`, `502`) | `Сервер вернул внутреннюю ошибку (HTTP <код>). Проверьте логи службы server.` |

### 4.2. Конфигурационные и сетевые ошибки на стороне CLI

| Ситуация | Сообщение в `stderr` |
| :--- | :--- |
| Не заданы `SERVER_URL` или `CLIENT_API_KEY` в `clients/cli/.env` | `Ошибка конфигурации CLI: не заданы SERVER_URL или CLIENT_API_KEY. Скопируйте clients/cli/.env.example в clients/cli/.env и заполните параметры.` |
| Некорректный формат `SERVER_URL` (`httpx.UnsupportedProtocol` / `InvalidURL`) | `Ошибка конфигурации CLI: некорректный адрес SERVER_URL («<значение>»). Укажите адрес вида http://127.0.0.1:8000.` |
| Сервер недоступен (`httpx.ConnectError`) | `Не удалось подключиться к серверу по адресу <SERVER_URL>. Убедитесь, что сервис server запущен и доступен по сети.` |
| Превышен таймаут ожидания сокета (`httpx.TimeoutException`) | `Сервер не ответил за <N> с. Для управляющих команд фактическое выполнение на Raspberry Pi неизвестно — проверьте статус через system status.` |

| Обрыв соединения при скачивании видео | Файл `<out>.part` удаляется; сообщение: `Загрузка видео прервана. Повторите команду snap video.` |
